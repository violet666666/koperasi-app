# Mobile Generic Per-Unit Laporan — Design Spec (Fase 7b)

**Date:** 2026-07-04
**Status:** Design approved (shared-helper DRY extraction, full V1 read-only); pending spec review → plan
**Branch:** `railway-migration` (auto-deploys API on push; mobile UI deploys via EAS build #5)
**Phase:** Fase 7b (second half of Fase 7 field-ops). Follows Fase 7a (Kas/Bank). Web has `/unit/[unitSlug]/laporan` (~2100-line page) shared by all 10+ unit types; mobile has only a Cuci-Mobil-specific screen backed by a broken minimal API.

## Problem

Mobile operators can only see a laporan for **Cuci Mobil** (`LaporanCuciMobilScreen`). For every other unit (toko, resto, cafe_lsp, barbershop, fitness, laundry, fotocopy, playstation), there's no mobile laporan. The existing `GET /api/mobile/reports/unit` is **architecturally broken** for general use: hardcoded 50/50 bagi-hasil (cuci-only logic forced on all units), queries only `UnitTransaction` (0 for toko/resto), uses `OperationalExpense` instead of `CashBankTransaction`. It's "accidentally correct" only for Cuci Mobil.

## Goal

A generic **mobile per-unit laporan** — one screen that shows the laporan for ANY unit, mirroring the web page's read-only blocks. Built DRY by **extracting the web route's data logic into a shared helper** that both web + mobile call (avoids the drift bug class that recurred in earlier fases).

## Approach (decided: shared helper + full V1 read-only)

Extract the web `GET /api/unit/[slug]/laporan` route's data logic (date-range compute + 3-model queries + aggregation + paginate) into `getUnitLaporanData({...})` in `src/lib/services/unit-laporan.ts`. The web route keeps its session auth + access control, then calls the helper. A new mobile route adds JWT auth (`getMobileUserWithScope`) + `canAccessUnit` scope, then calls the SAME helper. Web behavior is unchanged (mechanical refactor). A pure `computePeriodRange` sub-helper is unit-tested (the only testable piece — the rest is DB-bound).

The mobile screen is read-only, full V1: period chips, summary cards, payment-method breakdown, paginated transaction list, collapsible operational expenses/incomes, + conditional unit-specific blocks (F&B dine-in/takeaway, Cuci bagi-hasil/SHU/plate, store HPP/netProfit). No CRUD, print, or export in V1.

## Components

### 7b-1 — Shared helper `src/lib/services/unit-laporan.ts` (extract from web route)

Extract everything after the web route's auth/access-control (currently `route.ts` lines ~55-448) into:
```ts
import { prismaRead } from "@/lib/prisma";
// (other imports the web route uses: storeSaleUnitTypeFilter, unitTypeFilter, isSameUnit, isAutoGeneratedPiutang)

export interface UnitLaporanParams {
  unitType: string;            // e.g. "cuci_mobil" (already slug→type converted by caller)
  period: string;              // today|week|month|year|custom
  dateFrom?: string;           // for custom
  dateTo?: string;
  page: number;
  perPage: number;
  isExport: boolean;
  sortBy: string;              // transactionDate|transactionNo|amount
  sortOrder: "asc" | "desc";
}

export async function getUnitLaporanData(p: UnitLaporanParams): Promise<{
  unitType: string; unitSlug: string; periodLabel: string; dateFrom: string; dateTo: string;
  summary: { /* totalPendapatan, totalTransaksi, tunai, qris, potongGaji, dineIn, takeaway, counter, dineInCount, takeawayCount, counterCount, takeawaySurchargeTotal, totalPengeluaran, totalPemasukan, potonganSHUMember, jumlahCuciAnggota, shuPerCuci, laba, totalHPP, totalWriteOff, netProfit */ };
  transactions: Array<{ id; date; no; description; memberName; memberNrp; paymentMethod; amount; status; type; vehiclePlate }>;
  pagination: { page; perPage; total; totalPages };
  operationalExpenses: Array<{ id; date; transactionNo; description; amount; receiptImagePath; paymentMethod }>;
  operationalIncomes: Array<{ /* same shape */ }>;
}>
```
- Uses `prismaRead` (read replica) like the web route.
- `usesStoreSales = !["cuci_mobil","simpan_pinjam","investasi_modal_jp"].includes(unitType)` drives whether StoreSale/HPP is computed.
- **Web route refactor (mechanical, behavior-preserving):** replace lines ~55-448 with `const data = await getUnitLaporanData({ unitType, period, dateFromParam, dateToParam, page, perPage, isExport, sortBy, sortOrder }); return NextResponse.json({ data });`. The auth/access-control (lines 27-43) stays. **Verify response shape is byte-identical** before/after (the page must not break).

### 7b-1b — Pure period-range helper + unit tests (TDD)
Extract the WIB (+7) date-range computation into a PURE function `computePeriodRange(period, dateFrom?, dateTo?): { start: Date; end: Date; periodLabel: string; dateFromIso: string; dateToIso: string }` (no `new Date()` for "now" at the boundary — accept a `now: Date` param so it's deterministic + testable). Unit-test: today/week (Monday-start)/month/year/custom ranges in WIB, periodLabel formatting ("Juni 2026"), custom validation. (This is the testable piece — keeps the refactor honest.)

### 7b-2 — Mobile API `GET /api/mobile/reports/unit-laporan/[unitType]`

**File:** `src/app/api/mobile/reports/unit-laporan/[unitType]/route.ts` (import `getMobileUserWithScope` from `../../../middleware`, `canAccessUnit` from `@/lib/mobile-auth-scope`, `getUnitLaporanData` + `computePeriodRange` from `@/lib/services/unit-laporan`).

**Gate + scope:**
```ts
const user = await getMobileUserWithScope(request);
if (!user || !["operator","admin","admin_sp"].includes(user.role)) return 403;
const { unitType } = await params;            // params: Promise<{unitType}>
if (!canAccessUnit(user, unitType).allowed) return 403;   // operator bypass; admin → own unit (alias family); fail-closed
```
Parse `?period=&dateFrom=&dateTo=&page=&perPage=&sortBy=&sortOrder=&export=` (mirror web query params), call `getUnitLaporanData(...)`, return `{ data }`. `console.error` catch → 500. **`params: Promise<...>` + `await params`** (Next.js async-params).

### 7b-3 — Screen `mobile/src/screens/operator/LaporanUnitScreen.tsx`

Read-only, full V1. One screen with an in-screen unit selector (operator browses all units; admin effectively limited to their unit via the API gate).
- **Unit selector** (top): horizontal chips/dropdown of UNIT_TYPES — tap to switch unit (re-fetches).
- **Period chips:** today / week / month (+ a month picker for custom month). Re-fetch on change.
- **Summary cards (universal):** Total Pendapatan, Pengeluaran Ops, Laba Bersih (summary.laba), Jumlah Transaksi.
- **Payment-method breakdown:** Tunai / QRIS / Potong Gaji (summary.tunai/qris/potongGaji).
- **Unit-specific (conditional on unitType):**
  - F&B (`resto`, `resto_cafe`, `coffe_latar`, `cafe_lsp` — use the repo's `isRestoUnit`/alias check): Dine-In / Takeaway / Counter cards (+ nota counts, takeaway surcharge).
  - Cuci Mobil: Bagi Hasil 50/50 card (pendapatan kotor, bagian karyawan, bagian koperasi), Potongan SHU (Rp 2,000 × jumlah cuci anggota); vehicle plate shown in tx list.
  - Store units (`usesStoreSales` → toko/resto/cafe_lsp): HPP (`summary.totalHPP`) + Laba Bersih Akurat (`summary.netProfit`) — data already in the response.
- **Transaction list (paginated, infinite scroll):** date, description, member/pelanggan, method badge (cash/qris/salary_cut), amount, voided indicator.
- **Operational expenses + incomes (collapsible sections):** date, description, method, amount.
- States: loading, error+retry, empty. `log.*` only.

## RBAC
- Mobile route: operator/admin/admin_sp gate + `canAccessUnit(user, unitType).allowed` (operator bypass; admin → own unit alias-family; fail-closed 403). **Use `.allowed`** (ScopeDecision object — the Fase 7a lesson).
- Web route access control UNCHANGED (still session-based, isOperator/isSameUnit).
- The helper is unit-agnostic (no auth) — both routes gate before calling it.

## Test plan
- **Unit (Vitest):** `computePeriodRange` (today/week-Monday/month/year/custom in WIB, periodLabel, custom validation). This is the regression guard for the refactor.
- **Refactor safety:** the web `/api/unit/[slug]/laporan` response shape must be byte-identical before/after extraction (the implementer verifies by comparing the helper's return to the old inline build; the web page must render unchanged). Run any existing web laporan tests (none found — so verify structurally + manually).
- **Manual (mobile):** switch units (operator), each unit's summary/method/tx list renders; F&B shows dine-in/takeaway; cuci shows bagi-hasil + plate; toko shows HPP/netProfit; period chips re-fetch; admin scoped to own unit (other → 403); kasir no menu.

## Conventions / constraints
- **DRY:** `getUnitLaporanData` is the single source of truth for the laporan computation — web + mobile both call it. No duplication of the query/aggregation logic.
- **Web route refactor is mechanical + behavior-preserving.** Do NOT change the response shape or the auth. Verify before/after.
- **Use `.allowed` on `canAccessUnit`** (ScopeDecision object — Fase 7a lesson; the Fase 4c routes already do this correctly).
- `params: Promise<...>` + `await params` in the mobile route.
- `log.*` only in the mobile screen; `console.error` in server routes.
- `prismaRead` for the helper (read replica, like web).
- The broken `GET /api/mobile/reports/unit` (+ its Cuci Mobil consumer) is NOT removed in Fase 7b — it stays for backward compat; the generic screen supersedes it. Deprecation is a later cleanup.
- API deploys via Railway push; the screen ships via a future EAS build #5.

## Scope EXCLUSIONS (V1)
- No admin CRUD (add/edit/delete operational expenses/incomes) — web only.
- No "Kirim ke Operator" submit-review flow.
- No Excel export, no print layout, no receipt-image viewing.
- No top-products / menu-category analytics (web doesn't compute these either).
