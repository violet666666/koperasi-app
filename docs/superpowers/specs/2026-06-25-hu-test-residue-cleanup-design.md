# Design — Haji & Umrah Test-Residue Cleanup

**Date:** 2026-06-25
**Target DB:** Production Neon (`neondb` @ `ep-little-feather-a1of8czc-pooler.ap-southeast-1.aws.neon.tech`) — the shared dev+prod DB powering `primkoppol.site` and local dev (`DATABASE_URL` in `.env`).
**Branch:** `railway-migration`
**Status:** Design approved 2026-06-25; pending spec review → implementation plan.

---

## 1. Problem

The Haji & Umrah (H&U) unit accumulated E2E Playwright test residue in the production Neon database between 2026-06-11 and 2026-06-25. The unit's entire transactional surface is test data: there is exactly **one** H&U savings account in the whole DB (`HU-776-10-1715`, on real member 776 "A'AN ANDRIONO"), and 100% of its activity was generated by E2E specs (`haji-umrah-full`, `-comprehensive`, `-talangan`, `-bagi-hasil`) plus billing runs. The residue pollutes H&U lists, laporan, SHU income (admin fee + bagi-hasil spread), and the Bank BRI cash balance.

The 7 E2E specs have **no teardown** (`afterEach`/`afterAll`) — confirmed by reading all of them. Only `haji-umrah-bagi-hasil.spec.ts` self-voids, but voided rows still remain.

## 2. Goal

Remove all H&U test residue so the unit is **pristine** (only seed products TH/TU/TLH/TLU + the admin user remain, ready for real use), while:
- Preserving real member 776 (and all other members).
- Preserving the documented admin login `adminhajiumrah@koperasi.com`.
- Keeping Bank BRI (`CashBankAccount` 9) correct — reversing exactly the test inflation.
- Never touching non-H&U data (SP loans, other units' CB rows, etc.).

## 4. Approach

A single Prisma script `scripts/cleanup-hu-test-residue.ts` with two modes:
- **`--dry-run` (default):** computes the manifest dynamically, prints the hit-list + per-account balance deltas + a go/no-go summary. Writes no changes. Re-uses the same identification logic as the diagnose probes so the live manifest (not hardcoded IDs) drives deletion.
- **`--apply`:** runs the entire deletion inside one `prisma.$transaction([...])` so any error rolls everything back.

### 4.1 Identification (dynamic, not hardcoded)
The script re-derives IDs at runtime so it stays correct even if rows shifted:
1. `huSavingsProductIds` = `SavingsProduct.where(type in [tabungan_haji, tabungan_umrah])`.
2. `huAccountIds` = `SavingsAccount.where(productId in huSavingsProductIds)`.
3. `huSavingsTxnIds` = `SavingsTransaction.where(accountId in huAccountIds)`.
4. `cbToDelete` = `CashBankTransaction.where(OR: unitType=haji_umrah, OR (referenceType ~ savings AND referenceId in huSavingsTxnIds))`.
5. `bagiDistIds` = `BagiHasilDistribution.where(periodLabel ~ E2E OR ~ TEST OR status=voided)`.
6. `talanganLoanIds` = loans whose application has `notes ~ E2E/Playwright` OR `linkedSavingsAccountId in huAccountIds`, AND product type `talangan_*`.
7. `testProductIds` = `SavingsProduct.where(code in [TEST_COMPREHENSIVE, TEST_ADMIN_CRUD, ADMIN_CRUD_TEST, ADMIN_SETUP_TEST] OR code ~ TEST)`.
8. `huBillingItemIds` = `BillingItem.where(unitType=haji_umrah)`.

**Safety guards (script aborts if any triggers):**
- Any H&U `SavingsAccount` whose transactions are NOT all test → abort (mixed real account). Today all are test, but this protects against future drift.
- Any `SavingsTransaction` on an H&U account whose `createdBy` is neither `727` (operator) nor `1612` (adminhajiumrah) → abort + flag for manual review.
- Any `BagiHasilDistribution` with `status != voided` → abort (would delete a live distribution).
- Any talangan `Loan` with `status != voided` → abort.
- Any `SavingsProduct` selected for deletion that has > 0 accounts or transactions → abort.
- Count of `cbToDelete` outside the expected band (e.g., > 60) → abort.

### 4.2 Deletion order (inside one transaction, leaf-first)
1. `bagiHasilItem.deleteMany(where distributionId in bagiDistIds)`
2. `bagiHasilDistribution.deleteMany(where id in bagiDistIds)`
3. `loanPayment.deleteMany` + `loanSchedule.deleteMany` (where loanId in talanganLoanIds — expect 0)
4. `loan.deleteMany(where id in talanganLoanIds)`
5. `loanApplication.deleteMany(where id in talanganAppIds)`
6. Compute per-`accountId` net delta from `cbToDelete`; for each, `cashBankAccount.update({ data: { currentBalance: { decrement/increment: delta } } })`.
7. `cashBankTransaction.deleteMany(where id in cbToDelete)`
8. `billingItem.deleteMany(where id in huBillingItemIds)`
9. `savingsTransaction.deleteMany(where id in huSavingsTxnIds)`
10. `savingsAccount.deleteMany(where id in huAccountIds)`
11. `savingsProduct.deleteMany(where id in testProductIds)`

Steps 6 and 7 together keep `CashBankAccount.currentBalance` consistent with the surviving ledger rows. Decrementing before deleting the CB rows is safe because both are in the same transaction.

### 4.3 Backup
Before `--apply`, the script writes a CSV snapshot of every row about to be deleted (all columns) to `scripts/backups/hu-residue-<UTC-timestamp>.csv` (timestamp generated by the script via `new Date().toISOString()`). This file is the restore source if anything must be re-inserted.

### 4.4 Post-run verification
After `--apply`, the script re-runs the read-only checks and prints:
- `count(SavingsAccount where product.type in H&U)` == 0
- `count(CashBankTransaction where unitType=haji_umrah)` == 0
- `count(BagiHasilDistribution)` == 0
- `count(BillingItem where unitType=haji_umrah)` == 0
- `count(SavingsProduct where code ~ TEST)` == 0
- `CashBankAccount(9).currentBalance` == 1,418,651,787
- `User` 1612 still present; products TH/TU/TLH/TLU still present.

## 5. Risk & Mitigation

| Risk | Mitigation |
|---|---|
| Deleting real member data | Member 776 itself is never deleted; only its test H&U account. H&U `BillingItem` filter scoped to `unitType=haji_umrah` so member 776's SP-loan billing items (if any) are untouched. |
| Bank BRI balance drift | Net delta computed from the actual CB rows (not hardcoded); decrement is exact −Rp 6,329,000; post-run asserts the expected ending balance. |
| Shared CashBook account (acct 9 used by SP loans too) | Only the 41 H&U-linked CB rows are deleted; SP-loan CB rows (`referenceType=Loan:*`, other ids) are excluded by the identification logic. |
| FK violations | Leaf-first order; bagi-hasil items cascade; transaction wraps everything. |
| Future drift (new test runs add rows) | Guards abort on mixed/unknown creators; script is idempotent and re-runnable. |
| Wrong DB | Script prints masked `DATABASE_URL` + asserts it is the Neon host before any write. |
